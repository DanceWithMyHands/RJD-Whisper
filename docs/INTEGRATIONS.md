# Интеграции: распознавание речи (ASR) и бот видеоконференций

Документ описывает (1) как сейчас подключается распознавание аудио, (2) как ASR
должен разворачиваться в продакшене на инфраструктуре РЖД и по каким правилам к
нему обращаться, и (3) концепцию реального бота ВКС (Телемост / Cisco).

---

## 1. ASR сейчас: провайдеры и переключение

Распознавание вынесено за интерфейс `TranscriptionProvider`
(`backend/app/providers/transcription.py`). Провайдер выбирается переменной
`ASR_PROVIDER`:

| Значение | Реализация | Когда использовать |
|----------|-----------|--------------------|
| `stub` | детерминированный демо-транскрипт (без реального аудио) | разработка, демо, запись через бота-стаб |
| `openai_compatible` | POST `/audio/transcriptions` (Groq / OpenAI / self-hosted Whisper) | тестовые прогоны на реальном аудио, прод через внутренний шлюз |
| `nim` | Nvidia NIM ASR (REST) | прод на инфраструктуре с NIM-контейнерами |

Загруженный файл идёт в провайдер, дальше LLM-модуль выделяет поручения. Для записи
через бота (реального аудио нет) всегда используется `stub`.

### Быстрый тест через Groq (бесплатно)

Groq отдаёт OpenAI-совместимый эндпоинт с `whisper-large-v3`, отлично работает с
русским и быстрый.

1. Получить бесплатный ключ: https://console.groq.com → API Keys.
2. В `backend/.env`:
   ```env
   ASR_PROVIDER=openai_compatible
   ASR_API_BASE_URL=https://api.groq.com/openai/v1
   ASR_API_KEY=gsk_...        # ваш ключ
   ASR_MODEL=whisper-large-v3
   ASR_LANGUAGE=ru
   ```
3. `docker compose up --build` → на экране «Загрузка аудио» загрузить файл.

Тот же коннектор работает с **OpenAI** (`ASR_API_BASE_URL=https://api.openai.com/v1`,
`ASR_MODEL=whisper-1`) и с любым **self-hosted** сервером, отдающим совместимый ответ
(faster-whisper-server, vLLM, speaches и т.п.) — меняется только базовый URL.

### Поддерживаемые форматы загрузки

`mp3, wav, m4a, ogg, oga, opus, flac, webm, mp4, mpeg, mpga, aac, wma`
(проверка на бэкенде, эндпоинт `POST /api/v1/meetings/{id}/audio/transcribe`).

> Примечание: Whisper не делает диаризацию (разделение по говорящим). Для
> загруженного аудио реплики идут без привязки к участникам. Диаризация — отдельный
> шаг (pyannote.audio / NeMo) и выносится в следующую итерацию.

> **OpenRouter** для ASR **не подходит** — это шлюз к текстовым/чат-моделям, эндпоинта
> транскрипции аудио у него нет. Для ASR используем Groq/OpenAI-совместимый путь или NIM.

## 2. ASR в продакшене на серверах РЖД

Главное требование РЖД — данные совещаний (включая ПДн и потенциально
конфиденциальную информацию) **не должны покидать внутренний контур**. Поэтому в
проде ASR разворачивается self-hosted во внутренней сети.

### Варианты развёртывания (по возрастанию «тяжести»)

1. **faster-whisper-server / speaches** (CTranslate2) в Docker/K8s на GPU-узле.
   Отдаёт OpenAI-совместимый `/v1/audio/transcriptions` → подключается текущим
   провайдером `openai_compatible`, меняется только `ASR_API_BASE_URL` на внутренний
   адрес. Самый простой путь миграции.
2. **vLLM с Whisper** — если уже есть vLLM-кластер под LLM, можно поднять и ASR там же.
3. **NVIDIA Riva / NIM** (`parakeet`, `canary`) — промышленное решение с потоковым
   распознаванием и диаризацией, GPU-оптимизация. Подключается провайдером `nim`
   (`NIM_BASE_URL`, `NIM_API_KEY`). Ближе всего к «нейронка на серверах РЖД».

### Схема в контуре

```
[Фронт] → [FastAPI backend] → [внутренний ASR-сервис (GPU)] 
                            → [S3 (MinIO) внутри контура: хранение аудио]
                            → [LLM-сервис (Qwen, self-hosted) для поручений]
```

Бэкенд не зависит от конкретного ASR — только от URL/токена в конфиге.

### Правила доступа (как получать доступ к нейронке)

- **Сеть**: ASR-сервис доступен только из внутренней сети/VPN; наружу не публикуется.
  Файрвол/security group разрешает обращения только с хостов backend.
- **Аутентификация сервис-сервис**: mTLS (взаимные сертификаты) либо сервисный токен.
  Токен/сертификаты хранятся в секрет-менеджере (HashiCorp Vault / k8s Secrets), а не
  в коде и не в репозитории; в приложение приходят через переменные окружения.
- **Авторизация**: отдельная сервисная учётка с минимальными правами (только вызов
  транскрипции), ротация ключей по регламенту ИБ РЖД.
- **Данные**: аудио и транскрипты — в S3 внутри контура, шифрование at-rest и in-transit
  (TLS). Срок хранения и удаление — по политике РЖД (ПДн). Доступ к bucket — по IAM-политике.
- **Аудит**: логирование обращений к ASR (кто, когда, какой meeting_id), без тела аудио.
- **Ресурсы/масштаб**: GPU-узлы под нагрузку; длинные записи обрабатываются асинхронно
  через очередь (Celery/RQ + воркеры), статус совещания `processing → done/failed`.

### Чек-лист миграции test → prod

- [ ] Поднять внутренний ASR (faster-whisper-server или NIM) на GPU.
- [ ] `ASR_PROVIDER=openai_compatible` + `ASR_API_BASE_URL=https://asr.internal.rzd/...`
      (или `nim` + `NIM_BASE_URL`).
- [ ] Токен/сертификаты — из Vault, не в .env репозитория.
- [ ] S3 и БД — внутри контура, шифрование, политика хранения ПДн.
- [ ] Очередь и воркеры для длинных записей; таймауты и ретраи.
- [ ] Диаризация (pyannote/NeMo) при необходимости разделения по говорящим.

## 3. Бот видеоконференции (Телемост / Cisco) — концепция

Сейчас бот реализован стабом (`backend/app/providers/bot.py`): имитирует подключение,
запрос согласия и выход. Реальная интеграция требует корпоративных доступов и
медиа-инфраструктуры, поэтому ниже — целевая концепция.

### Общий паттерн «медиа-бот»

1. Бот как **виртуальный участник** присоединяется к встрече по ссылке/ID.
2. Запрашивает **согласие на запись** у участников (требование ТЗ).
3. Получает **аудиопоток** (микс или по-участникам — для диаризации), пишет в S3.
4. По завершении встречи передаёт аудио в наш пайплайн (ASR → LLM → поручения).

### Cisco

- **Webex** имеет официальные API: REST для встреч/записей (Recordings API) и
  платформу ботов; для живого аудио — **Media SDK / SIP-медиабот**, подключающийся как
  участник и получающий RTP. Это наиболее реалистичный путь для Cisco-контура.
- **Jabber/Cisco Meeting Server (CMS)**: запись организуется штатными компонентами
  (Recorder), далее файл забирается нашим бэкендом и отправляется в ASR.
- Что нужно: корпоративный Webex/CMS-тенант, права администратора, регистрация
  бота/приложения, разрешения на запись, сетевой доступ к медиаплоскости (SIP/RTP).

### Яндекс Телемост

- Публичного API для ботов и серверной записи у Телемоста фактически нет (на момент
  написания). Реалистичные варианты:
  - **Headless-участник**: автоматизированный клиент (браузер/нативный) заходит по
    ссылке как участник и захватывает системный звук; хрупко, но не требует API.
  - **Договорённость с платформой** об интеграции/записи на уровне организации.
  - Если в РЖД используется связка с Яндекс 360 — уточнить доступные корпоративные
    возможности записи.
- Что нужно: подтверждение наличия API/возможностей записи у платформы, корп-доступы,
  юридическое основание записи (согласие участников).

### Промежуточный мост (рекомендация)

Пока нет реального бота — **экран «Загрузка аудио» закрывает потребность**: модератор
включает штатную запись в Телемост/Cisco, выгружает файл и загружает в систему →
получает транскрипт и поручения. Это рабочий продакшен-сценарий без зависимости от
ботового API.

### Что требуется от РЖД для реального бота

- Корпоративные аккаунты и админ-доступ к платформе(ам) ВКС.
- Разрешение/регламент на запись совещаний (юридически, согласие участников).
- Сетевой доступ к медиаплоскости (SIP/RTP) и/или регистрация бота в тенанте.
- Инфраструктура под медиабот (отдельный сервис, возможно с GPU/CPU под микширование).
